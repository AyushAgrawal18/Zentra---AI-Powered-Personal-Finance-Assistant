# 1. Purpose

This document defines how data is stored, related, validated, and maintained inside Zentra.

It establishes:

- Schema design
- Naming conventions
- Key strategy
- Relationship rules
- Migration process
- Performance guidelines

Every database object must conform to this document.

---

# 2. Architectural Goals

The database architecture should provide:

- Data integrity
- High performance
- Scalability
- Easy maintenance
- Consistent naming
- ACID compliance
- Efficient querying
- Reliable backups

---

# 3. Non Goals

Version 1 intentionally excludes:

- Multi-region replication
- Multi-tenant databases
- Database sharding
- Event sourcing
- Polyglot persistence

Future versions may introduce these capabilities.

---

# 4. Database Overview

Version 1 uses a single PostgreSQL database.

Primary data includes:

- Users
- Transactions
- Categories
- Budgets
- Goals
- Payment Intents
- AI Insights
- Notifications
- User Settings

PostgreSQL is the single source of truth.

---

# 5. Technology Stack

Database

- PostgreSQL 16+

Migration Tool

- Node.js migration scripts

Connection

- pg

Administration

- pgAdmin (Development)

ORM

- None

All database access occurs through repositories.

---

# 6. Design Philosophy

The schema follows these principles:

- Third Normal Form (3NF)
- Minimal redundancy
- Explicit relationships
- Strong referential integrity
- Predictable naming
- UUID primary keys
- Soft deletes where applicable

Business rules belong in services—not in database triggers.

---

## Tables

Use:

```

Examples

- users
- transactions
- budgets
- payment_intents

## Columns

Use:

```

Examples

- created_at

- user_id

## Constraints

# 8. Primary Keys

Every table uses:

```
UUID
```

Rules:

- Generated by PostgreSQL
- Immutable
- Never reused
- Never exposed for sequential inference

Auto-incrementing integer IDs are prohibited.

---

# 9. Foreign Keys

Every relationship must use foreign keys.

Example:

```
transactions.user_id

↓

users.id
```

Rules:

- Enforce referential integrity
- Use cascading rules only when appropriate
- Never leave orphaned records

---

# 10. Audit Fields

Every business table should contain:

```
id

created_at

updated_at

deleted_at
```

Optional:

```
created_by

updated_by
```

Audit fields support traceability and soft deletion.

---

# 11. Soft Deletes

Business records should use:

```
deleted_at TIMESTAMP NULL
```

Rules:

- Deleted records remain in the database.
- Queries ignore soft-deleted rows by default.
- Permanent deletion is exceptional.

Authentication tokens and temporary records may use hard deletes.

---

# 12. Transactions

Multi-step operations must use PostgreSQL transactions.

Examples:

- Transaction creation
- Payment reconciliation
- CSV import
- SMS import

Rules:

- BEGIN
- COMMIT
- ROLLBACK

Database consistency takes priority over performance.

---

# 13. Constraints

Use constraints wherever appropriate.

Examples:

- NOT NULL
- UNIQUE
- CHECK
- FOREIGN KEY

Application validation complements—but never replaces—database constraints.

---

# 14. Indexing Strategy

Indexes should be created for:

- Primary keys
- Foreign keys
- Frequently filtered columns
- Frequently sorted columns
- Frequently searched columns

Avoid unnecessary indexes that slow writes.

---

# 15. Relationships

Relationship types:

- One-to-One
- One-to-Many

Version 1 does not require many-to-many relationships.

All relationships should be documented in `relationships.md`.

---

# 16. Migrations

Schema changes must occur only through migrations.

Migration rules:

- Sequential
- Version-controlled
- Reversible where practical
- Tested before production

Manual schema changes are prohibited.

---

# 17. Security

The database enforces:

- Authentication
- Least-privilege access
- Encrypted connections
- Secure backups
- Input parameterization

Repositories must always use parameterized queries.

---

# 18. Performance

Performance strategies include:

- Proper indexing
- Query optimization
- Connection pooling
- Pagination
- Select only required columns
- Avoid N+1 query patterns

Performance should be measured before optimization.

---

# 19. Design Principles

- PostgreSQL is the source of truth.
- SQL exists only in repositories.
- Every relationship uses foreign keys.
- UUIDs identify every entity.
- Soft deletes preserve historical data.
- Business logic never belongs in SQL.

---

# 20. Locked Decisions

Version 1 database decisions:

- PostgreSQL
- UUID primary keys
- Repository pattern
- No ORM
- Snake_case naming
- Soft deletes
- Parameterized queries
- Migration-based schema management

Changes require updating this document.

---

# 21. Future Evolution

Future improvements may include:

- Read replicas
- Partitioned tables
- Materialized views
- Full-text search
- Advanced indexing
- Database monitoring
- Automated archival

These enhancements should preserve the existing schema contracts.
